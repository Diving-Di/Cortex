# Diary Listener 重构软件设计说明书（SDD）

> 文档状态：规划中  
> 目标产品：以本地优先的 Markdown 笔记、AI 整理、周期报告和“回忆书”为核心的 Web 应用  
> 当前基线：React 18 + TypeScript + Webpack、FastAPI + SQLAlchemy 2.0；项目尚未产生正式数据，数据库直接采用 PostgreSQL  
> 状态维护规则：本文所有功能初始均为未完成。只有代码实现、测试通过并满足对应验收标准后，才能将 `[ ]` 更新为 `[x]`。

## 1. 文档目的

本文描述 Diary Listener 从“AI 聊天 + 轻日记 Demo”重构为本地优先笔记应用的需求范围、系统架构、数据模型、接口、安全策略、迭代计划和完成清单。本文同时作为后续开发的执行计划与验收依据。

## 2. 项目目标

### 2.1 核心目标

- 建立可长期维护的笔记数据模型，统一支持普通笔记、日报、周报和月报。
- 提供 Markdown 编辑、预览、自动保存、标签、附件和全文搜索能力。
- 将现有同步 AI 聊天升级为可配置、异步、流式且可取消的 AI 服务。
- 基于用户笔记实现 AI 整理、周期报告以及带来源引用的回忆问答。
- 统一使用 PostgreSQL，提供可靠的备份、恢复和 Markdown 导出。
- 保留 React、FastAPI 和 SQLAlchemy 技术栈，逐步替换 Demo 结构。
- 支持多个相互隔离的个人租户，每个注册用户自动拥有且只拥有一个个人租户。

### 2.2 非目标

以下内容不属于首个 MVP：

- 向量数据库或独立向量检索服务。
- 桌面悬浮组件。
- 自动更新系统。
- 企业级计费、跨区域部署和超大规模租户分库。
- 数据库正文与 Markdown 文件双向实时同步。
- 多套厂商专用 AI SDK；首版统一使用 OpenAI 兼容协议。
- 复杂的编辑器行内 AI 补全。
- 工作收益等非核心统计功能。

## 3. 设计原则

1. **PostgreSQL 是正文唯一权威来源**：首版笔记正文存入数据库，Markdown 仅作为导入和导出格式。
2. **本地优先**：应用未配置 AI 或网络不可用时，笔记功能仍须完整可用。
3. **渐进式重构**：每次迭代均应形成可运行、可测试的增量，避免一次性推倒重写。
4. **数据安全优先**：所有模式变更必须通过 Alembic 管理；项目从全新 PostgreSQL Schema 开始。
5. **AI 不直接覆盖原文**：AI 整理和报告生成须先预览，用户确认后才能写入。
6. **引用可追溯**：回忆问答和报告应保存并展示来源笔记。
7. **最小暴露面**：附件不得通过公开静态目录访问，敏感配置不得返回前端或写入仓库。
8. **租户边界不可绕过**：业务资源以租户为主要隔离边界，后端不能信任客户端单独提交的 `tenant_id`。
9. **一人一租户**：个人用户注册后自动创建唯一的个人租户，不提供团队成员、邀请、角色或租户切换。

## 4. 用户与核心场景

### 4.1 目标用户

- 个人用户：注册后自动获得一个独立个人租户，管理自己的笔记、附件、AI 配置、配额和备份。
- 实例运维管理员：只负责实例健康、数据库迁移和全局运维，不通过普通业务接口查看租户正文。

### 4.2 核心使用场景

1. 用户在工作台快速记录一段文字，并将其保存或交给 AI 整理。
2. 用户按日期创建和编辑日报、周报、月报或普通笔记。
3. 用户为笔记添加标签和多个附件，并安全地查看或下载附件。
4. 用户通过关键词、日期、类型和标签查找历史笔记。
5. 用户选择一个时间范围，生成带来源的周期报告。
6. 用户在“回忆书”中提问，系统检索笔记后生成带引用的回答。
7. 用户备份全部数据，并能在新环境中恢复。
8. 多个用户同时使用同一实例，各自只能访问自己的个人租户数据。

## 5. 总体架构

```text

    |
    | HTTP + SSE
    v
React + TypeScript
    |
    | /api/*
    v
FastAPI
    |-- 身份认证与个人租户上下文
```

### 5.1 开发运行方式

- 前端：保留 Webpack 5，开发服务器默认监听 `127.0.0.1:5173`。
- 后端：Uvicorn/FastAPI，默认监听 `127.0.0.1:8000`。
- 前端通过 Webpack DevServer 代理访问 `/api`。
- 开发、测试和生产统一使用 PostgreSQL，避免不同数据库行为造成迁移偏差。

### 5.2 为什么当前项目继续使用 Webpack

当前仓库已经具有可运行的 `webpack.config.js`、TypeScript Loader、CSS Loader、HTML 模板、开发代理、文件指纹和生产构建流程。继续使用 Webpack 的主要收益是：

- **迁移成本低**：无需为更换构建工具同时修改脚本、环境变量、代理规则、静态资源路径和容器配置，可以把时间投入笔记与多租户核心功能。
- **生产构建能力成熟**：支持 Tree Shaking、按路由代码分割、动态导入、长期缓存文件名和公共依赖拆包。
- **配置可控**：Loader 与 Plugin 体系适合后续接入 Markdown、Web Worker、PWA、代码高亮及特殊静态资源处理。
- **开发代理已验证**：现有 `/api` 与 `/media` 代理可平滑调整为新版 `/api/v1` 和鉴权附件接口。
- **大型应用扩展空间**：当页面和功能增多时，可以通过 `splitChunks`、懒加载和构建分析控制包体积；未来若拆分独立前端，也可评估 Module Federation。
- **构建结果稳定**：锁定 Node、Webpack、Loader 和 Plugin 版本后，适合 Windows 安装包和离线发布流程。

继续使用 Webpack 的代价是配置较多、冷启动和增量编译通常慢于 Vite。当前决策是保留 Webpack，并通过持久化缓存、并行类型检查、按路由懒加载和构建分析优化；只有出现明确的开发效率瓶颈时，才单独立项评估 Vite，避免把工具迁移与业务重构绑定在一起。

### 5.3 本地发布方式

- MVP 可由启动器启动 FastAPI，并由 FastAPI 或独立静态服务提供前端构建产物。
- Nginx 仅在确有统一反向代理需求时引入，不作为笔记核心功能的前置条件。
- 所有本地服务默认只监听 `127.0.0.1`。

### 5.4 多个人租户服务端部署

- 多用户跨设备访问时，通过 Nginx 或同类网关提供 HTTPS，FastAPI 不直接暴露公网端口。
- PostgreSQL 作为唯一业务数据库，允许多个无状态 FastAPI 实例共享数据库与对象存储。
- 附件可从本地目录演进到 S3 兼容对象存储，但下载仍通过鉴权接口或短期签名 URL。
- 生产环境必须配置可信域名、严格 CORS、请求限流、租户配额、审计日志和备份保留策略。
- 本地开发通过 Docker Compose 或本机服务运行 PostgreSQL，与测试和生产保持一致。

## 7. 数据设计

### 7.1 数据目录


PostgreSQL 通过 `DATABASE_URL` 或等价的安全配置连接，不在应用数据目录保存数据库文件。附件数据库记录使用相对路径，不保存依赖特定机器的绝对路径。

### 7.2 核心数据表

#### users

| 字段 | 类型 | 说明 |
|---|---|---|
| id | integer | 主键 |
| username | varchar | 唯一用户名 |
| email | varchar | 唯一邮箱 |

#### tenants

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键，由服务端生成 |

- 不建立 `tenant_memberships`、`tenant_invitations` 或角色表。
- 租户不可转让给其他用户；注销账户时进入保留期，之后统一清理其租户数据。

| 字段 | 类型 | 说明 |
|---|---|---|

#### tags / note_tags

- `tags` 保存租户内的标签名称和可选颜色。
- `note_tags` 建立笔记与标签的多对多关系。
- 同一租户下的标签名称应唯一。

#### conversations / messages / message_sources

- `conversations` 保存对话标题、模式、所属租户和发起用户。
- `messages` 保存用户与 AI 消息、生成状态及错误信息。
- `message_sources` 保存 AI 消息引用的笔记 ID、片段、相关度和排序。

#### ai_providers / ai_usage_records

- `ai_providers` 保存租户级显示名称、兼容接口地址、默认模型和能力标记；也可引用实例级公共 Provider。
- API Key 必须使用环境变量、系统凭据或应用加密机制存储，不允许通过普通查询接口明文返回。
- `ai_usage_records` 保存 `tenant_id`、调用用户、模型、请求类型、输入/输出 Token、耗时、结果状态和时间，用于租户配额与审计。

#### app_settings

- 保存实例级或租户级非敏感应用设置，并明确 `scope`。
- 设置必须带明确类型和默认值，不允许任意 JSON 覆盖关键安全配置。

### 7.3 多租户隔离模型

采用 **单个 PostgreSQL 数据库、共享表、显式 `tenant_id`** 的行级隔离方案。每个用户只对应一个个人租户，不存在团队成员或跨租户协作。

#### 租户上下文解析

1. 用户通过 Token 完成身份认证。
2. 后端根据认证用户查询唯一的 `tenants.user_id`，生成只读 `TenantContext(user_id, tenant_id)`。
3. 业务 API 不接受客户端指定 `tenant_id`，也不提供租户切换入口。
4. 每个数据库事务开始时执行 `SET LOCAL app.current_tenant_id = '<uuid>'`。
5. service 和查询层只接收可信的 `TenantContext`，并显式加入 `tenant_id` 过滤。
6. PostgreSQL Row Level Security 再根据 `current_setting('app.current_tenant_id')` 限制行访问。

#### 查询和约束规则

- notes、revisions、attachments、tags、conversations、messages、sources、AI 用量、报告任务和审计记录都必须携带 `tenant_id`。
- 所有唯一约束必须包含正确作用域，例如 `(tenant_id, name)`、`(tenant_id, type, note_date)`。
- 关联查询不仅校验资源 ID，还校验两端 `tenant_id` 一致，避免跨租户 ID 拼接。
- 禁止在 API 中提供未限定租户的通用 `get_by_id(id)`；应使用 `get_by_id(tenant_id, id)`。
- PostgreSQL 必须启用 Row Level Security，并为应用运行角色启用 `FORCE ROW LEVEL SECURITY`；数据库 owner/迁移角色与应用角色分离。
- 搜索索引必须可按 `tenant_id` 过滤；检索后在进入 AI 上下文前再次核对租户。

#### 租户生命周期与数据

- 注册用户时在同一事务中自动创建唯一个人租户。
- 登录后租户由服务端自动解析，不支持创建第二个租户、邀请成员或切换租户。
- 账户与租户删除默认采用延迟软删除，并在保留期内允许恢复。
- 备份、恢复和 Markdown 导出默认仅针对当前租户；实例管理员全量备份是独立运维能力。
- 附件路径使用 `attachments/<tenant_id>/YYYY/MM/...`，同时仍以数据库所有权校验为准。
- 所有环境统一使用 PostgreSQL；生产备份使用 `pg_dump`/`pg_restore` 与附件备份包配合完成。

### 7.4 搜索索引

- 使用 PostgreSQL `pg_trgm` 与 GIN 索引支持中文标题、正文和摘要的模糊检索。
- 可增加生成列或 `tsvector` 支持英文全文搜索；中文分词插件作为后续可选增强，不作为部署硬依赖。
- 搜索查询必须首先限定 `tenant_id`，并受 RLS 策略约束。
- 搜索同时支持日期范围、笔记类型和标签过滤。
- 实现前必须用真实中文样本验证召回率；若运行环境不支持合适分词，则保留 `LIKE` 搜索降级路径。

### 7.5 全新数据库初始化

- 数据库按全新项目初始化，不包含任何历史数据处理流程。
- 首个 Alembic revision 直接创建 PostgreSQL 完整初始 Schema。
- 初始 Schema 包含用户、个人租户、认证、笔记、标签、附件、会话、AI 配置及审计所需表。
- 首个 revision 同时创建 `pg_trgm` 扩展、必要索引、约束、RLS Policy 和 `FORCE ROW LEVEL SECURITY` 配置。
- 提供空库初始化命令和开发测试数据生成命令；测试数据不得进入生产环境。
- 后续所有结构变化继续通过新的 Alembic revision 演进，不修改已经发布的历史 revision。

## 8. API 设计

### 8.1 通用约定

- API 前缀统一为 `/api/v1`。
- 业务 API 不接收 `tenant_id`；后端从认证用户解析其唯一个人租户。
- 错误响应至少包含稳定错误码、用户可读消息和可选字段错误详情。
- 列表接口统一支持分页，禁止无上限返回全部数据。
- 时间统一以 ISO 8601 传输；数据库明确采用 UTC 或带时区时间策略。
- 修改接口应防止自动保存覆盖更新后的内容，可使用 `updated_at` 或版本号进行乐观锁校验。

| POST | `/api/v1/reports/generate` | 生成周期报告 |
| POST | `/api/v1/memory/chat` | 回忆问答，SSE 输出 |
| GET | `/api/v1/settings` | 查询安全的应用设置 |
| PATCH | `/api/v1/settings` | 修改允许的设置 |
| POST | `/api/v1/backups` | 创建备份 |
| POST | `/api/v1/backups/restore` | 恢复备份 |
| POST | `/api/v1/exports/markdown` | 导出 Markdown |

## 9. 前端功能设计

### 9.1 页面路由

| 路由 | 页面 | 主要能力 |
|---|---|---|
| `/login` | 登录/注册 | 登录、注册和错误反馈 |
| `/` | 工作台 | 快速记录、今日摘要、最近笔记 |
| `/notes` | 笔记本 | 类型、日期和标签筛选 |
| `/notes/:id` | 编辑器 | Markdown 编辑、预览、自动保存、附件 |
| `/reports` | 周期报告 | 日/周/月报告选择、生成和查看 |
| `/memory` | 回忆书 | 检索增强对话和来源引用 |
| `/search` | 搜索 | 关键词与组合过滤 |
| `/settings` | 设置 | AI、数据目录、备份和应用设置 |

### 9.2 前端技术选择与 Webpack 配置

- Webpack 5：继续作为构建与开发服务器，启用生产 Tree Shaking、内容哈希和 `splitChunks`。
- `webpack-dev-server`：代理新版 API，并支持 SPA history fallback。
- 持久化 filesystem cache：降低重复构建耗时。
- 动态 `import()`：按工作台、笔记、报告、回忆书和设置路由拆包。
- 构建分析：定期检查首屏包体和重复依赖，设置合理的性能预算。
- React Router：页面路由。
- TanStack Query：服务端数据请求、缓存和失效管理。
- Zustand：仅用于少量全局 UI 状态，不复制服务端数据。
- CodeMirror 6：Markdown 源码编辑。
- `react-markdown`：Markdown 预览。
- Mermaid、KaTeX、Shiki 在核心编辑闭环稳定后按需加入。

### 9.3 个人租户体验

- 登录后自动进入当前账户唯一的个人空间，不显示租户选择器。
- 前端不提交或缓存可修改的 `tenant_id`，租户上下文完全由后端认证结果决定。
- 设置页可以展示个人空间名称、配额和用量，但不能将空间转让或添加成员。

### 9.4 自动保存策略

- 内容变化后防抖保存，建议间隔 800～1500ms。
- 页面显示 `未保存`、`保存中`、`已保存`、`保存失败` 状态。
- 保存失败时保留本地编辑内容并允许重试。
- 服务端版本冲突时停止覆盖，提示用户比较或重新加载。
- 切换路由或关闭页面前，对未完成保存给出提示。

## 10. AI 与检索设计

### 10.1 AI 客户端

- 使用异步 `httpx.AsyncClient`。
- 首版统一支持 OpenAI 兼容的 Chat Completions 接口。
- 支持超时、有限重试、用户取消、SSE 流式返回和结构化错误。
- 日志不得记录 API Key、完整认证头或不必要的私人笔记正文。
- 未配置 AI 时返回明确的能力不可用状态，不伪装成真实 AI 回复。

### 10.2 AI 整理

```text
快速记录
  -> 用户选择整理类型
  -> 服务端构造提示词
  -> AI 返回结构化候选内容
  -> 前端预览差异
  -> 用户确认
  -> 创建或更新笔记并保留修改前版本
```

### 10.3 周期报告

- 用户选择日报、周报或月报及目标日期。
- 系统先按日期范围检索来源笔记。
- 无来源时不得生成看似真实的报告。
- 报告草稿必须展示来源笔记列表。
- 用户确认后保存为相应类型笔记。
- MVP 仅支持手动触发，定时生成在正式版增强阶段实现。

### 10.4 回忆书

```text
用户问题
  -> 提取日期范围和关键词
  -> 按租户、日期、标签过滤
  -> PostgreSQL pg_trgm/全文索引检索候选笔记
  -> 按标题、日期和相关性排序
  -> 截取相关片段并控制上下文长度
  -> AI 流式生成回答
  -> 保存并展示引用来源
```

- 检索必须始终带可信的 `tenant_id` 条件，并记录实际调用用户。
- 无充分证据时，回答应明确说明没有找到相关记录。
- 引用至少包含笔记 ID、标题、日期和命中片段。

## 11. 安全设计

- Token 只在创建时返回原文，数据库仅保存安全哈希。
- Token 必须具有过期和撤销机制。
- 生产环境限制 CORS 来源，禁止通配来源与凭据组合。
- 上传限制单文件大小、允许类型和租户总配额。
- 文件类型同时检查扩展名、声明 MIME 和文件签名。
- 存储文件名由服务端生成，原始名称仅作为元数据。
- 附件读取必须验证资源属于当前认证用户对应的个人租户。
- 所有业务资源查询必须显式限定可信租户上下文。
- 禁止客户端通过修改路径、请求头或请求体中的 `tenant_id` 越权访问。
- 租户设置、导出、恢复和高风险删除必须写入审计日志。
- AI Key 不进入 Git、不写普通日志、不通过设置 API 明文返回。
- 本地发布端口默认只监听 `127.0.0.1`。
- 备份文件可能包含全部私人数据，应向用户明确提示并限制路径穿越。

## 12. 可靠性、性能与可观测性

### 12.1 PostgreSQL 配置

- 开发、测试和生产使用兼容的 PostgreSQL 主版本。
- 应用连接与 Alembic 迁移使用不同数据库角色。
- 为所有租户业务表启用并强制执行 RLS。
- 每个请求事务设置 `SET LOCAL app.current_tenant_id`，事务结束后自动清除。
- 配置连接池上限、连接超时、语句超时和空闲事务超时。
- 外键、唯一约束和必要索引由 Alembic 管理。
- 关键写操作使用短事务。
- 文件操作和数据库操作使用可补偿流程，失败时不留下不可识别的孤立状态。

### 12.2 日志

- 记录请求 ID、级别、模块、错误码和必要上下文。
- 区分开发日志和发布日志。
- 对认证信息、AI Key、私人正文进行脱敏。
- 提供日志轮换，避免数据目录无限增长。

### 12.3 性能目标

- 常规笔记列表和详情在本地数据规模下应快速响应。
- 所有列表均分页，附件使用流式响应。
- AI 生成应尽快返回首个 SSE 事件，并允许取消。
- 搜索索引更新不得要求全量重建。

## 14. 分次实施计划

每次实现均应保持主分支可运行。若某次实现范围过大，可拆成多个提交，但不得在未达到完成定义时勾选对应功能。

### 第 0 次：需求与工程基线

**目标**：冻结 MVP 范围，明确全新 PostgreSQL 工程的实现边界。

**实现内容**：

- 保存现有代码、API 和运行方式基线，仅用于判断需要替换的 Demo 实现。
- 确定本地数据目录规则和环境配置规则。
- 确定 PostgreSQL 版本、连接方式、数据库角色和空库初始化方式。
- 定义版本号、迁移规则和功能状态维护规则。

**验收标准**：

- MVP 和非目标没有歧义。
- 明确项目没有需要迁移或保留的历史数据。
- 全新环境的 PostgreSQL 初始化路径明确且可重复执行。
- 后续每个功能都有稳定编号和验收标准。

### 第 1 次：后端工程骨架与数据库迁移

**目标**：建立可演进的后端基础。

**实现内容**：

- 重组 `core`、`models`、`schemas`、`services` 和 `api`。
- 引入 Alembic，停止使用 `create_all()` 作为正式迁移手段。
- 将数据库运行时统一为 PostgreSQL，配置连接池、超时和数据库角色。
- 为租户业务表建立 PostgreSQL RLS 策略与请求事务上下文。
- 增加统一配置、异常响应、日志和健康检查。
- 建立 pytest 和首批 API 测试。

**验收标准**：

- 空数据库可由迁移命令初始化。
- 迁移可以升级和回退。
- 应用启动不再隐式修改正式数据库结构。
- 健康检查和基础测试通过。

### 第 2 次：Webpack 工程优化与前端框架升级

**目标**：建立页面化、可测试的前端框架。

**实现内容**：

- 保留 Webpack 5，整理开发与生产配置。
- 启用持久化缓存、生产 Tree Shaking、内容哈希和 `splitChunks`。
- 建立路由级动态导入和构建包体分析。
- 引入 React Router 和受保护路由。
- 建立页面布局和 feature 目录。
- 引入 TanStack Query，统一 API 错误处理。
- 建立前端测试和生产构建检查。

**验收标准**：

- 开发服务器、生产构建和路由刷新正常。
- 生产产物具备稳定内容哈希，主要页面按路由拆包。
- 未登录用户不能进入受保护页面。
- API 错误有统一且可读的展示。

### 第 3 次：认证与个人多租户安全基础

**目标**：修复现有 Demo 中最直接的安全问题。

**实现内容**：

- Token 改为哈希存储，增加过期、注销和撤销。
- 建立 tenants 和审计模型，并以 `tenants.user_id` 唯一约束保证一人一租户。
- 注册时在同一事务中创建个人租户。
- 实现可信 `TenantContext(user_id, tenant_id)`，业务 API 不接收客户端租户 ID。
- 应用层过滤与 PostgreSQL RLS 同时生效。
- 限制 CORS 和服务监听地址。
- 增加登录、注销和无权限访问测试。
- 敏感配置迁移到安全配置来源。
- 清理 Docker Compose 演示密码和不必要端口暴露。

**验收标准**：

- 数据库中不存在可直接使用的原始 Token。
- 已注销或已过期 Token 无法访问资源。
- 用户无法访问其他个人租户的数据。
- 即使遗漏应用层租户过滤，RLS 测试仍能阻止跨租户访问。
- 个人用户不手动配置租户也能直接进入默认个人空间。

### 第 4 次：笔记数据模型与初始 Schema

**目标**：在全新 PostgreSQL 数据库中建立统一笔记领域模型。

**实现内容**：

- 新增带 `tenant_id` 的 notes、note_revisions、tags、note_tags 和 attachments 表。
- 实现普通、日报、周报和月报类型约束。
- 通过 Alembic 创建完整初始表、约束、索引和 RLS Policy。
- 实现笔记 CRUD、分页、日期导航和租户隔离。
- 提供开发测试数据生成工具，不包含生产默认账户或密码。

**验收标准**：

- 全新 PostgreSQL 空库可以一次升级到最新 Schema。
- 测试用户注册后能自动创建唯一个人租户。
- 四类笔记均可增删改查。
- 同一租户同一日期/周期不会意外产生重复默认报告。

### 第 5 次：Markdown 编辑与自动保存

**目标**：形成可日常使用的笔记编辑闭环。

**实现内容**：

- 笔记列表、编辑页和日期导航。
- CodeMirror Markdown 编辑和预览。
- 防抖自动保存、保存状态和失败重试。
- 乐观锁或版本检测，避免覆盖冲突。
- 保存关键版本并支持查看、恢复。

**验收标准**：

- 刷新和重启应用后内容不丢失。

### 第 6 次：标签与安全附件

**目标**：支持笔记分类和多附件管理。

**实现内容**：

- 附件鉴权读取和用户配额。
- 文件与数据库操作的失败补偿。

**验收标准**：

- 用户只能访问自己的附件。

### 第 7 次：全文搜索与筛选

**目标**：可靠查找历史笔记。

**实现内容**：

**验收标准**：

**目标**：让用户能够掌控并迁移自己的数据。

**验收标准**：

2. 执行对应单元、接口、集成或端到端测试。
3. 对照该次实现的验收标准进行人工检查。
4. 仅将已经实现且验证通过的具体功能从 `[ ]` 改为 `[x]`。
5. 不得因为“代码已开始”“大致可用”或“依赖已安装”而勾选。
6. 若功能回归失败，应将状态恢复为 `[ ]`，直到重新验证通过。
7. 每次状态更新应在提交说明中列出功能编号，例如 `DL-123`。

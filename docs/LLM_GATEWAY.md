# 大模型网关接入规范

> 文档状态：阶段一已实施并验收
> 适用范围：Cortex 后端的通用 AI 生成、AI 工作流（整理/报告/回忆/知识问答）和定时报告
> 关联文档：`SDD.md`
> 参考资料：[有没有用过大模型的网关框架？网关层解决了什么问题？](https://xiaolinnote.com/ai/tools/16_llm_gateway.html)

## 1. 背景与目标

Cortex 当前通过 OpenAI 兼容的 Chat Completions 接口调用大模型，并由后端环境变量维护模型服务地址、密钥和默认模型。随着模型调用场景增加，重试、故障转移、模型路由、配额、成本统计和安全策略不应继续分散在业务代码中。

本项目计划在应用后端与模型供应商之间增加独立的大模型网关：

```text
浏览器
  |
Cortex 后端
  |
  | OpenAI 兼容协议、网关虚拟密钥
  v
大模型网关
  |---------- 主模型
  |---------- 备用模型
  `---------- 其他兼容模型
```

网关接入目标：

- 保持业务层使用统一的 OpenAI 兼容协议。
- 集中保管模型供应商的真实 API Key。
- 支持逻辑模型到实际模型的路由和故障转移。
- 统一处理限流、配额、超时、重试和熔断。
- 获得准确的 token、成本、延迟和错误统计。
- 在满足租户隔离和隐私要求的前提下评估缓存。

网关不是 Cortex 的业务功能，不应在前端暴露为普通用户设置。

## 2. 现状与可行性

当前实现已完成透明接入：

- `backend/internal/ai/eino_client.go` 的 `EinoClient` 通过 Eino OpenAI 兼容组件统一调用
  `{base_url}/chat/completions`，并支持 SSE 流式响应。
- `backend/internal/config/config.go` 通过 `AI_API_KEY`、`AI_BASE_URL` 和 `AI_MODEL` 读取网关配置。
- 通用 AI、整理/报告/回忆/知识问答工作流和定时报表均复用同一客户端。
- `docker-compose.yml` 将应用统一指向 LiteLLM Proxy。
- `backend/internal/ai/eino_client_test.go` 覆盖基本 SSE 解析。

因此，网关只要提供 OpenAI 兼容的 `/v1/chat/completions` 接口，第一阶段即可通过替换后端配置接入，无需改变前端协议或核心业务接口。

现有 `AiProvider` 数据表和 `/api/v1/ai/providers` 接口只保存租户 Provider 信息，实际模型调用仍读取部署环境配置。网关实施前必须确定唯一配置来源，禁止数据库 Provider 配置与网关路由同时控制实际模型而产生歧义。

网关验收范围以 `/api/v1/ai/stream`、AI 工作流（整理/报告/回忆/知识问答）和定时报告为准。

## 3. 技术选型原则

优先采用独立部署的成熟网关，不在 Cortex 内部自行实现完整网关能力。

候选方案：

| 方案 | 适用情况 | 备注 |
| --- | --- | --- |
| LiteLLM Proxy | 需要广泛模型支持、路由、预算和可观测能力 | 首选候选；必须锁定版本、校验镜像并持续关注安全公告 |
| New API / One API | 主要使用国产或 OpenAI 兼容模型 | 部署较简单，需单独验证流式协议、配额和故障转移 |
| Bifrost | 对网关延迟和吞吐有较高要求 | 引入前需验证运维成熟度和所需功能 |
| 托管网关 | 团队不希望自行运维网关 | 必须先评估日记内容的数据处理位置、保留策略和合规风险 |

最终选型必须满足：

- 支持 OpenAI 兼容 Chat Completions 和流式 SSE。
- 支持虚拟密钥，真实供应商密钥只存在于网关。
- 支持逻辑模型、备用路由、超时、有限重试和熔断。
- 能按虚拟密钥或请求元数据统计 token、成本、延迟和错误。
- 不在普通日志中保存完整 Prompt、日记正文、认证头或密钥。
- 能关闭缓存；如启用缓存，必须支持严格的租户命名空间。
- 镜像版本可固定，依赖和升级过程可审计。

### 3.1 已选方案与版本基线

- [x] 网关选用 LiteLLM Proxy。
- [x] 版本锁定为 `main-v1.77.7-stable`。
- [x] 多架构 OCI digest 锁定为 `sha256:cc6255644a32511355bc53c5d4d0ca7b3c5df45ad881225ff57e8a88e083c563`。
- [x] linux/amd64 manifest digest 已验证为 `sha256:2db5f02380bd676e8d9338d2294e9ebaddfe8a6d73468f074d04b51c97b276bc`。
- [x] 配置文件固定为仓库根目录 `litellm-config.yaml`。
- [x] 缓存关闭；错误正文日志关闭，spend 记录写入独立管理数据库。

选择 LiteLLM Proxy 的原因是当前 Go 客户端使用 OpenAI 兼容 Chat Completions/SSE，接入不需要修改业务协议；同时 LiteLLM 原生支持 Kimi/OpenAI 兼容上游、逻辑模型、fallback、重试和后续预算治理。当前不同时引入 New API、One API 或 Bifrost，避免维护两套网关语义和验收矩阵。

首期路由：

| 逻辑模型 | 顺序 | 实际上游 | 用途 |
| --- | ---: | --- | --- |
| `diary-default` | 1 | Kimi `kimi-k2.5` | 主模型；已通过真实 SSE、整理、报告和回忆验收 |
| `diary-deepseek-fallback` | 2 | DeepSeek `deepseek-chat` | 第一备用，由 LiteLLM 在主模型失败时调度 |
| `diary-openai-fallback` | 3 | OpenAI `gpt-5.6` | 第二备用；当前本地 OpenAI 账户为 `insufficient_quota` |

LiteLLM 配置以 Kimi 为主路由，并依次将 DeepSeek、OpenAI 放入 fallback。OpenAI 额度恢复前，OpenAI fallback 只用于验证路由行为，不作为可用性保障。

## 4. 配置规范

Cortex 后端继续只读取以下部署配置：

```env
AI_BASE_URL=http://llm-gateway:4000/v1
AI_API_KEY=<网关签发的虚拟密钥>
AI_MODEL=diary-default
```

规则：

- `AI_BASE_URL` 指向网关，不直接指向模型供应商。
- `AI_API_KEY` 是网关虚拟密钥，不是供应商真实密钥。
- `AI_MODEL` 优先使用稳定的逻辑模型名，例如 `diary-default`。
- 供应商地址、真实密钥、部署名、权重和备用路由只在网关配置中维护。
- API Key 不进入前端状态、浏览器存储、URL、Cookie、数据库业务字段、日志、审计详情或备份包。
- 网关管理端口不得公开暴露；仅应用调用端口允许在内部网络访问。
- 开发、测试和生产环境使用不同的虚拟密钥、预算与日志空间。

### 4.1 知识库 Embedding

当前 Compose 由内部 `embedding-service` 加载固定 revision 的
`iic/nlp_gte_sentence-embedding_chinese-small`，个人知识库 v2 通过该服务生成
Embedding（512 维），Backend 经 OpenAI 兼容接口直接调用。模型返回 512 维向量，支持中英文和中英混合语料。服务不暴露宿主机端口。

Backend 默认不发送 `dimensions`，但仍严格校验响应必须为 512 维；
`RAG_EMBEDDING_SEND_DIMENSIONS` 保持 `false`。配置如下：

```env
RAG_EMBEDDING_BASE_URL=http://embedding-service:4000/v1
RAG_EMBEDDING_API_KEY=<LiteLLM virtual key>
RAG_EMBEDDING_MODEL=iic/nlp_gte_sentence-embedding_chinese-small
RAG_EMBEDDING_DIMENSIONS=512
RAG_EMBEDDING_SEND_DIMENSIONS=false
```

原文件、提取文本、父子分片和 embedding 返回值都保存在本地部署环境；只有生成向量所需的
child 文本和查询文本会发送给内部 Embedding 服务。精排由内部 `reranker-service` 的
`BAAI/bge-reranker-v2-m3` 完成，同样不暴露宿主机端口。

## 5. 路由与可靠性规范

网关至少配置一个逻辑模型：

```text
diary-default
  1. 主模型
  2. 同等能力的备用模型或备用部署
```

不同任务需要独立路由时，可增加：

- `diary-chat`：交互式流式生成，优先低首 token 延迟。
- `diary-organize`：笔记整理和结构化输出，优先遵循指令能力。
- `diary-report`：周期报告，允许更长上下文和较长超时。

首期可以全部映射到 `diary-default`，但名称应允许未来拆分。

可靠性规则：

- 仅对连接失败、超时、429 和可恢复的 5xx 执行有限重试。
- 已经向客户端输出内容的流式请求不得从头自动重试，以免生成重复内容。
- 重试采用带抖动的指数退避，并设置总耗时上限。
- 不对鉴权失败、参数错误和内容安全拒绝进行重试。
- 主路由达到失败阈值后允许切换备用路由。
- 网关不可用时，后端返回稳定的应用错误，不得绕过网关偷偷使用供应商真实密钥。
- 应用层与网关层不能同时进行不受控重试；实施时应明确各层职责，避免重试放大。

## 6. 租户、隐私与日志

日记正文属于高敏感个人内容。网关必须延续 Cortex 的多租户隔离原则。

应用向网关传递观测元数据时，应使用不可直接识别个人身份的内部标识，并至少区分：

- 租户。
- 请求类型，如 `chat`、`organize`、`report`。
- 调用环境。
- 请求追踪 ID。

安全要求：

- 禁止将用户邮箱、姓名或其他直接身份信息作为网关标签。
- 默认不记录完整 Prompt、完整响应和日记正文。
- 若故障排查临时开启正文采样，必须限定环境、比例和时间，完成后关闭并清理。
- 指标和管理界面必须设置访问控制。
- 租户 A 的请求、响应、缓存和统计明细不得被租户 B 访问。
- 网关供应商或托管服务的数据保留、训练使用和跨境处理策略必须在生产启用前完成评估。
- 网关日志错误信息返回应用前应脱敏，不得暴露上游密钥、内部地址或供应商响应正文。

## 7. 用量与成本统计

当前应用内 `AiUsageRecord` 使用字符数估算 token。接入网关后，网关统计作为供应商成本和 token 用量的准确来源，应用数据库仍可保留面向产品功能的请求记录。

两者职责：

| 数据来源 | 用途 |
| --- | --- |
| Cortex `AiUsageRecord` | 租户内产品统计、请求状态、业务类型和用户体验指标 |
| 网关指标 | 准确 token、模型成本、上游延迟、路由、重试和供应商错误 |

如网关能在流式完成后返回标准 usage，后续可将准确值回填应用记录；不能可靠取得时，应保留估算值并明确标记为估算，禁止将其用于账单结算。

预算和限流至少按环境及应用虚拟密钥配置。若按租户执行预算，必须确保租户标识不可伪造，并由后端生成而不是接受前端直接传入。

## 8. 缓存规范

### 8.1 默认策略

首期关闭语义缓存。不得启用跨租户或全局共享的 Prompt/响应缓存。

原因：

- 日记内容高度私密且强个性化。
- 语义相近不代表上下文、日期、来源笔记和期望答案相同。
- 错误命中可能向用户返回他人的内容，属于严重数据隔离事故。
- 聊天和笔记报告的输出可能随模型、系统提示词和来源内容变化。

### 8.2 可评估的精确缓存

完成网关稳定接入后，可先试验租户隔离的精确缓存。缓存键至少包含：

```text
tenant_id
request_type
model_or_route_version
system_prompt_version
generation_parameters
source_content_hash
normalized_request_hash
```

还必须满足：

- 使用加密存储和传输。
- 设置明确且较短的 TTL。
- 模型、系统提示词、生成参数或来源内容变化后自动失效。
- 支持按租户清除；租户删除或恢复数据时同步处理缓存。
- 缓存命中仍保持当前 SSE 输出契约。
- 指标只记录命中状态和耗时，不记录正文。

### 8.3 语义缓存启用门槛

只有在精确缓存运行数据证明存在明显重复请求，且完成隔离测试后，才能单独评估语义缓存。启用前必须：

- 仅对白名单请求类型开放。
- 使用租户独立的向量命名空间。
- 禁止不同租户之间的向量检索和答案复用。
- 通过离线测试选择相似度阈值，不直接照搬固定阈值。
- 为时间敏感和个性化请求提供强制绕过机制。
- 对误命中率、命中收益和数据删除行为建立测试。
- 明确 embedding 模型、向量库和缓存数据的保留策略。

聊天、回忆问答、包含日记正文的整理任务默认不进入语义缓存白名单。

## 10. 测试与验收标准

接入完成必须通过以下验证：

### 协议兼容

- SSE 内容能够逐块解析，并以 `[DONE]` 正常结束。
- 网关附加的 SSE 字段不会导致客户端解析失败。
- Unicode、多行内容和长响应保持完整。
- 客户端取消请求后，后端和网关能够停止不必要的上游生成。

### 路由与故障

- 主模型正常时请求不进入备用路由。
- 主模型发生连接失败、429 或可恢复 5xx 时按策略重试或故障转移。
- 401、403 和请求参数错误不会被重试。
- 流式输出开始后的故障不会产生重复片段。
- 网关不可用时应用返回统一错误，笔记的非 AI 功能仍正常。

### 安全与隔离

- 前端构建产物、浏览器存储、API 响应和普通日志中不存在真实供应商密钥。
- 网关管理接口不能从公开网络访问。
- Prompt 和日记正文默认不出现在网关普通日志和指标标签中。
- 租户间的指标明细和任何缓存均不可互相访问。
- 删除租户数据时，对应的可选缓存能够按策略清除。

### 统计与成本

- 每次请求可以按环境、请求类型和内部租户标识归属。
- 能区分最终模型、备用路由、重试次数、状态和延迟。
- 网关 token 统计与上游返回值一致或差异处于已说明的范围。
- 预算耗尽只影响对应虚拟密钥或租户，不影响其他租户。

### 回归

- `/api/v1/ai/stream` 自动化测试通过。
- AI 整理和报告集成测试通过。
- 定时报告成功、失败和无来源场景通过。
- 未配置网关虚拟密钥时继续返回 `AI_NOT_CONFIGURED`。

## 11. 非目标

本次网关接入不包含：

- 在设置页中提供供应商密钥、模型路由或连接测试。
- 允许浏览器直接调用网关或模型供应商。
- 在 Cortex 内部重新实现通用 LLM 网关。
- 默认启用全局缓存或跨租户语义缓存。
- 用网关替代应用自身的身份认证、租户鉴权和数据行级安全。
- 首期同时引入多个网关产品或复杂的跨区域多活部署。

## 12. 推荐决策

Cortex 应增加独立的大模型网关。首期重点是透明代理、密钥集中管理、可靠路由、配额和成本观测；缓存不是首期依赖。

语义缓存只有在严格租户隔离、数据保留和删除机制、离线误命中测试以及真实成本收益均得到验证后才能启用。任何无法提供租户级缓存命名空间的网关实现，都不得缓存 Cortex 的 Prompt 或响应。

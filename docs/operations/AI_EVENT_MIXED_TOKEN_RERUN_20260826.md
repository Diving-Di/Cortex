# AI 限量活动冷热混合流量复测（2026-08-26）

> 适用边界：Windows、Docker Desktop、本地单 backend Compose 环境。结果用于冷热混合用户旅程的
> 本地容量回归，不是生产 SLA。

## 模型

- Git Commit：`6d9649ca6d0592ada7443de977e2d19936471148` 加当前压测脚本工作树；
- 2,000 个用户：1,800 合格、200 不合格，库存 500；
- Token：热 70%、温 20%、冷 10%；热 Token 在预热阶段复用两次，温 Token 出现一次，冷 Token
  在测量阶段首次出现；
- 测量阶段固定 10,000 个请求：活动状态 4,500（45%）、资格 2,000（20%）、领取 2,000（20%）、
  领取结果 1,000（10%）、点数余额 500（5%）；
- 用户在页面查询后等待 1–5 秒，再执行资格、领取和可选结果查询；
- 预热阶段另有 3,200 个请求，不计入上述业务比例，但 k6 全局 HTTP 汇总包含预热请求；
- 本地单客户端 Claim IP 限流临时由 60 调整为 20,000，测试后恢复。

## 2,000 并发旅程失败容量点

2,000 个完整旅程同时启动时，13,200 个含预热请求在约 70.5 秒内完成，吞吐 187.21 req/s，HTTP
失败率 12.89%。状态、资格和 Claim 大量达到 15 秒客户端超时：

| 指标 | 结果 |
|---|---:|
| 状态查询 P95 | 3.82 s |
| 资格查询 P95 | 15.00 s |
| Claim P95 | 14.55 s |
| 结果查询 P95 | 12.11 s |
| 整体 P99 | 15.00 s |
| 客户端观测成功 / 售罄 / 不合格 / 非预期 | 471 / 540 / 148 / 841 |

客户端超时没有破坏数据库一致性。请求收敛后数据库仍为库存、Claim、唯一租户、库存槽和奖励各 500，
重复 Claim、重复奖励和未处理 Outbox 均为 0。该轮证明单 backend 无法承载 2,000 个同步完整旅程，
应归为瞬时峰值失败点。

资源采样 19 个样本：backend CPU 峰值 207.52%，PostgreSQL 154.55%，Redis 90.51%。

## 200 并发稳定轮

2,000 个旅程由 200 VU 执行，测量阶段约 51.7 秒；包括预热在内共 13,200 个请求，整体吞吐
163.81 req/s，HTTP 失败率 0%，整体 P95 1.77 秒、P99 2.59 秒。

## 结论

- 冷热混合场景的并发正确性通过：无超卖、无重复发奖、无重复 Claim；
- 200 并发下 Claim、整体 P99 和错误率通过，但三个读接口 P95 未达到初始体验门槛，因此整体不通过；
- 2,000 并发完整旅程明显超过本地单 backend 容量，虽然数据库最终一致；
- 下一步应先用单接口阶梯测试定位状态、资格和结果查询的认证、RLS、连接池与 SQL 成本，再测试
  1/2/3 backend；当前结果不能给出生产推荐容量。

原始 summary、console、facts 和资源 CSV 保存在本地忽略的
`artifacts/ai-event-k6-mixed-1787719188*`。测试用户、Token、资格笔记、Claim、reservation、库存槽和
点数记录已清理，活动恢复为 10 个名额、0 已领取。

## 定向优化后同口径复跑

使用包含投影统计读路径、Token 使用时间降频和活动页聚合接口的新 backend 镜像，严格复用 2,000 用户、
200 VU 和原五类独立请求比例复跑。由于同口径脚本仍调用独立接口，本轮只公平衡量前两项优化；聚合接口
减少页面请求数的收益不混入比较。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 状态查询 P95 | 2.28 s | 3.22 s | +41.2% |
| 资格查询 P95 | 1.19 s | 1.57 s | +31.9% |
| Claim P95 | 1.84 s | 1.73 s | -6.0% |
| 结果查询 P95 | 1.34 s | 1.61 s | +20.1% |
| 整体 P99 | 2.59 s | 3.51 s | +35.5% |
| HTTP 失败率 | 0% | 0% | 持平 |
| 吞吐 | 163.81 req/s | 161.35 req/s | -1.5% |

正确性仍全部通过：500 成功、1,300 售罄、200 不合格、0 非预期，数据库库存、Claim、唯一租户、
库存槽和奖励均为 500，重复项和 Outbox 积压均为 0。

资源峰值方面，backend CPU 从 211.16% 到 213.67%，基本持平；PostgreSQL CPU 从 102.67% 降至
61.36%，下降约 40.2%；Redis 从 23.87% 到 28.49%。这说明投影读路径显著减轻了数据库 CPU，但当前
200 VU 长尾没有同步改善，瓶颈更可能位于 backend CPU、认证连接池等待或本地 Docker 调度。单轮结果也
存在环境波动，不能把读接口 P95 回退直接归因于 SQL 变更。

结论：本轮优化降低了数据库成本并小幅改善 Claim，但未改善同口径用户体验门槛。下一步应使用新聚合
接口建立页面旅程新基线，并采集 `cortex_auth_database_pool_empty_acquire_total`、连接获取时长和 Go
profile，再决定是否增加认证缓存或横向扩容。

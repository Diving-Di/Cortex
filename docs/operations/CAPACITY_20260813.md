# 2026-08-13 Knowledge Retrieval 容量验收

测试使用临时合成租户，每篇文档一个 parent/child 和确定性 512 维向量；检索调用生产 `Store.SearchKnowledge`，
保留 `WithTx`、transaction-local RLS 与显式租户条件。每阶段执行 100 次串行检索，完成后级联删除合成租户，
数据库确认残留合成用户/租户均为 0。

| 文档数 | 装载 docs/s | p50 | p95 | p99 | 失败 | 关系增量 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 235.232 | 7.673 ms | 16.367 ms | 19.381 ms | 0/100 | 73,728 B |
| 1,000 | 633.839 | 32.295 ms | 45.536 ms | 48.381 ms | 0/100 | 925,696 B |
| 10,000 | 1,551.787 | 347.562 ms | 405.277 ms | 427.214 ms | 0/100 | 40,345,600 B |

首个瓶颈是 10,000 文档时 `eligible` CTE 上的向量/关键词候选扫描：p95 相比 1,000 文档扩大约 8.9 倍。
在继续扩大单租户语料前，应先用 `EXPLAIN (ANALYZE, BUFFERS)` 固化计划，并评估按租户/collection 缩小候选、
调优 HNSW 与将关键词/title 路径分开限流。当前 2 CPU/2 GiB backend 和 PostgreSQL 本机环境下，建议把
单租户 10,000 文档视为需要优化的容量边界，而不是已承诺 SLA。

该数据不含 HTTP、Embedding、Reranker、TTFT、LLM 总响应或并发饱和点；测试没有 AI 调用，因此 token 成本和
供应商费用记为未测量，不做估算。机器可读原始结果位于本地忽略的 `artifacts/capacity-20260813.json`，可用
`backend/scripts/knowledge_capacity.ps1` 重跑。
